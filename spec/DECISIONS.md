# Decisions

This ledger explains why active choices exist. It is not canonical authority.

If this file conflicts with a canonical owner, the canonical owner wins and this ledger must be corrected. Historical wording and superseded process decisions remain in Git history.

| ID | Decision | Canonical owner | Rationale / provenance |
|---|---|---|---|
| D-001 | The active repository must be self-describing and vendor-neutral. | `../CONSTITUTION.md` | A new reasoning session should understand the project without vendor-specific files, hidden prompts, or prior chat history. |
| D-002 | Keep a bounded explicit authority surface: README + Constitution + Objective + 12 learning-domain specs + 9 product/runtime design owners + this supporting ledger. | `../CONSTITUTION.md` | Product/runtime scope justifies independent design owners while reviews/research/evidence remain outside authority. |
| D-003 | Model Academic + General Training as the complete standard-IELTS scope; share constructs where IELTS shares them and use variant overlays only where the external exam differs. | `00-PRODUCT.md`, `02-IELTS-MODEL.md` | Supersedes the older “Academic first, GT later” semantic framing. Release sequencing may still be Academic-first, but GT is not a future construct. |
| D-004 | Canonical learning requirements are L1-agnostic; L1/localization is an overlay. | `00-PRODUCT.md` | IELTS competence does not change by first language, while explanation/remediation may. Legacy `FD-002`. |
| D-005 | Listening, Reading, Writing, Speaking are first-class skills; grammar/vocabulary/phonology are enabling Knowledge. | `03-SKILLS.md`, `04-KNOWLEDGE.md` | Aligns the learning model with IELTS scored sections without losing teachable prerequisites. Legacy `FD-003`. |
| D-006 | Learning-domain truth is implementation-agnostic. | `00-PRODUCT.md` | Technology consumes the learning system; it does not define it. Legacy `FD-006`. |
| D-007 | Progression is mastery/evidence-based while within-band path may adapt. | `09-PROGRESSION.md` | Stable outcomes with personalized path. Legacy `LD-001`. |
| D-008 | Core tutoring/feedback/assessment may operate without mandatory human review; human verification remains optional. | `00-PRODUCT.md`, `08-ASSESSMENT.md` | Preserve scalable operation while failing closed on unsupported productive judgments. Legacy `LD-002`. |
| D-009 | Feedback timing depends on learning stage and target. | `07-PRACTICE.md` | Universal immediate feedback conflicts with retrieval, transfer, fluency, and exam-independence goals. Legacy `LD-003`. |
| D-010 | Dependencies are Required, Recommended, or Independent; hard gates must be minimal. | `06-CURRICULUM.md`, `09-PROGRESSION.md` | Preserve prerequisite integrity without making every beneficial ordering a blocker. Legacy `LD-004`. |
| D-011 | Learning Progression and Exam Preparation are independent dimensions. | `09-PROGRESSION.md` | Exam-like/higher-demand exposure can aid readiness without becoming a certification shortcut. Legacy `LD-005`. |
| D-012 | Use six learning phases: Acquisition, Consolidation, Retrieval, Transfer, Fluency, Exam Readiness. | `07-PRACTICE.md` | Stable purpose vocabulary across training patterns. Legacy `LD-006`. |
| D-013 | Skill Leaves are atomic, stable-ID capabilities; no arbitrary leaf-count target. | `03-SKILLS.md` | Atomicity serves teaching, practice, assessment, and remediation. Legacy `SK-001..003`. |
| D-014 | Knowledge uses atomic objects with explicit Knowledge→Knowledge and Skill→Knowledge dependencies. | `04-KNOWLEDGE.md` | Prerequisites must resolve to learnable knowledge rather than vague labels. Legacy `KK-001..003`. |
| D-015 | Bands 3–9 are the structured learning range; Bands 0–2 are diagnostic/external boundaries. | `05-BANDS.md` | Preserve full scale awareness without inventing a detailed sub-Band-3 curriculum. Legacy `BD-001`. |
| D-016 | Exit criteria are hierarchical where needed: task threshold → skill-band threshold → progression decision. | `05-BANDS.md` | Prevent task requirements from disappearing into vague overall mastery. Legacy `BD-002`. |
| D-017 | Listening/Reading detailed per-band abilities are Blueprint Inference unless directly supported by official IELTS evidence. | `02-IELTS-MODEL.md`, `05-BANDS.md` | Receptive public scoring does not provide the same analytic descriptor structure as Writing/Speaking. Legacy `BD-003`. |
| D-018 | Curriculum orchestrates canonical objects by reference; it does not redefine them. | `06-CURRICULUM.md` | Pathway organization must not become another learning truth layer. Legacy `CR-001`, `CR-003`. |
| D-019 | Practice Types are reusable activity patterns; concrete exercises are instances. | `07-PRACTICE.md` | Stable learning strategy with replaceable/generated content. Legacy `PR-001`, `PR-003`. |
| D-020 | Assessment Types define reusable measurement roles; concrete tests/items are instances. | `08-ASSESSMENT.md` | Measurement semantics must not live inside item collections. Legacy `AM-001`, `AM-002`. |
| D-021 | Evidence sufficiency is claim-scoped; there is no universal attempt count or global confidence cutoff. | `08-ASSESSMENT.md` | Earlier provisional `N=2` / `0.80` heuristics were too strong as canonical policy; claim/evaluator calibration owns numeric thresholds. |
| D-022 | Learner state is semantic, not a storage schema. | `09-PROGRESSION.md` | Runtime learning truth should survive implementation changes. Legacy `PG-001`. |
| D-023 | Each IELTS skill progresses/certifies independently; overall Band is informational for learning progression. | `09-PROGRESSION.md` | Uneven profiles are normal. Supersedes the older synchronized four-skill gate. Legacy `PG-002`. |
| D-024 | Current certification may regress when new admissible evidence establishes regression; historical attainment remains. | `09-PROGRESSION.md` | Current truth and history are separate. Legacy Red-Team F2 resolution. |
| D-025 | Concrete content is reference-based and replaceable. | `10-CONTENT-MODEL.md` | Learning Units, items, stimuli, feedback, and tutoring patterns must not become parallel domain definitions. |
| D-026 | Go, Python, and TypeScript are the approved primary application languages. | `../CONSTITUTION.md` | Explicit polyglot baseline prevents accidental runtime-language sprawl. |
| D-027 | Implementation topology is responsibility-first; inside deployables, application code is feature/capability-first with layers introduced only for real boundaries. | `../CONSTITUTION.md`, `../design/06-implementation-stack.md` | Avoid language silos, pure horizontal layer-first growth, and ceremonial package trees while keeping ordinary feature changes local. |
| D-028 | Genuine cross-language boundaries have one explicit machine-readable contract owner; generated/local bindings are derived. | `../CONSTITUTION.md` | Prevent Go/Python/TypeScript mirror-schema drift. |
| D-029 | Use the same canonical domain vocabulary across languages while keeping language syntax idiomatic and wire identity exact. | `../CONSTITUTION.md`, `../design/06-implementation-stack.md` | Stable semantics across runtimes without normalizing Go, Python, and TypeScript to one casing/folder convention. |
| D-030 | Root verification must span every affected language and relevant cross-language contract. | `../CONSTITUTION.md` | A polyglot change is not verified because only one ecosystem is green. |
| D-031 | Separate Attempt → Observation → EvidenceFact → Readiness evaluation → Progression. | `08-ASSESSMENT.md`, `10-CONTENT-MODEL.md`, `09-PROGRESSION.md` | A response is not automatically evidence; evidence is not automatically mastery. |
| D-032 | Missing, conflicting, stale, and observed-below-requirement evidence are distinct epistemic states. | `08-ASSESSMENT.md`, `01-LEARNER-MODEL.md` | Unknown is not weakness; stale is not regression; conflict should not be averaged away. |
| D-033 | Claim outcomes use explicit semantic states rather than one readiness percentage. | `08-ASSESSMENT.md` | Required conditions must not be averaged away by stronger unrelated evidence. |
| D-034 | Adaptive planning follows GapEvaluation → ActionIntent → Learning Mechanism → Practice Type. | `09-PROGRESSION.md`, `07-PRACTICE.md` | Different gap types require different interventions. |
| D-035 | Learning Mechanism and Practice Type are separate concepts. | `07-PRACTICE.md` | A learning process and an executable activity pattern are different authorities. |
| D-036 | Spacing applies only to suitable reviewable targets; there is no universal scheduler for every IELTS capability. | `07-PRACTICE.md`, `09-PROGRESSION.md` | Vocabulary retrieval and integrated productive performance do not share one meaningful review object. |
| D-037 | Stale evidence alone never constitutes regression. | `09-PROGRESSION.md` | Regression requires later admissible below-threshold evidence; staleness only requires refresh. |
| D-038 | Learner skipping, preference, or friction are planning signals, not ability evidence. | `01-LEARNER-MODEL.md`, `09-PROGRESSION.md` | Agency may shape eligible delivery without contaminating mastery inference. |
| D-039 | Full mocks are readiness/re-evidence activities with learning side-effects, not certification shortcuts. | `07-PRACTICE.md`, `08-ASSESSMENT.md` | Broad integrated performance cannot replace targeted intervention or claim-scoped sufficiency. |
| D-040 | Guided success and same-item retry preserve narrower inference scope than independent/unseen performance. | `08-ASSESSMENT.md`, `10-CONTENT-MODEL.md` | Scaffolding and exposure change what performance can legitimately prove. |
| D-041 | Maintain a canonical `design/` plane downstream of learning specs. | `../CONSTITUTION.md` | Learner flow, product surfaces, API/runtime, providers, and coverage are independent design authorities but cannot redefine learning truth. |
| D-042 | The initial product surface contains 40 named feature capabilities. | `../design/01-skill-features.md` | Concrete feature ownership prevents teams from inventing inconsistent skill products while keeping feature identity separate from Skill Leaves. |
| D-043 | The initial app exposes 28 user-facing practice modes. | `../design/02-practice-catalog.md` | Learners need a concrete understandable catalog; topics/sources/variants compose modes rather than explode taxonomy. |
| D-044 | Media is a source substrate, not another learning taxonomy; arbitrary unofficial media extraction is not an assumed capability. | `../design/03-media-youtube.md` | Media practice is useful, but rights/transcript/source constraints remain first-class. |
| D-045 | The browser has one public product API through Go Core API; Python evaluator is internal only. | `../design/04-application-flows.md`, `../design/05-api.md` | Prevent runtimes from independently orchestrating learner state or duplicating policy. |
| D-046 | Framework families are TypeScript/React/Next.js for web, Go `net/http` + chi for Core API, and Python/FastAPI for evaluator/media analysis. Exact dependency patches belong to implementation lockfiles. | `../design/06-implementation-stack.md` | Architecture should freeze first-order responsibility and framework family without becoming stale release-note metadata. |
| D-047 | Productive evaluation is asynchronous from the browser; Python returns bounded observations/provenance/uncertainty and Go applies Assessment/Progression. | `../design/04-application-flows.md`, `../design/06-implementation-stack.md` | Evaluator latency/failure must not make evaluator infrastructure mastery authority. |
| D-048 | Learner goals are a `TargetProfile` constraint set, not only one overall Band. | `../design/00-learning-experience.md` | Real targets may include overall, per-skill, purpose, date, variant, and material delivery constraints. |
| D-049 | Planner recommendation is strong but learner changes operate only within eligible alternatives and never erase prerequisites/target conditions. | `../design/00-learning-experience.md`, `../design/04-application-flows.md` | Preserve agency without turning the planner into decoration or weakening the target. |
| D-050 | External services have a provider-neutral authority domain; Database, AI, and Identity are mandatory portability boundaries. | `../design/07-third-party-services.md` | Provider names must not become domain truth; privacy/quality/reliability eligibility precedes cost optimisation. |
| D-051 | Product coverage is condition-based and uses `MODELLED → COVERED → SUPPORTED_FOR_PRODUCT → VALIDATED`; condition statuses are a separate enum. | `../design/08-coverage-and-support.md` | Completeness requires executable conditions; `DEFINED/PARTIAL/NOT_APPLICABLE` must not masquerade as product target status. |
| D-052 | Intended complete standard-IELTS scope is Academic + General Training; IELTS Life Skills is outside the current Band-3→9 construct unless explicitly added. | `../OBJECTIVE.md`, `../design/08-coverage-and-support.md` | Shared standard constructs should not be duplicated; Life Skills is a different pass/fail construct. |
| D-053 | Imported founder decisions remain non-canonical research input. | `../CONSTITUTION.md` | Preserve prior reasoning/provenance without giving another repository automatic authority over this IELTS system. |
| D-054 | Product support/current evidence may support a target profile, but the app must not guarantee a specific future external IELTS result. | `../design/00-learning-experience.md`, `../design/08-coverage-and-support.md` | Route integrity, learner readiness, product support, and empirical validation are separate claims. |
| D-055 | Test variant and delivery mode are orthogonal dimensions: Academic/GT define construct differences; computer, Writing-on-Paper, and IELTS Online are delivery conditions and never redefine Band semantics. | `02-IELTS-MODEL.md`, `../design/00-learning-experience.md` | 2026 delivery changes affect exam-readiness interaction and target eligibility/acceptance, not the language construct. |
| D-056 | Diagnostic assessment reduces decision-relevant uncertainty and must preserve an explicit sampling ledger rather than fabricate a complete baseline. | `08-ASSESSMENT.md` | Quick/full flows can legitimately leave conditions unresolved; unsampled/unusable/pending is not weakness. |
| D-057 | Planner hard eligibility and candidate ranking are separate stages; ranking has no authority to make an invalid action valid. | `../design/04-application-flows.md` | Prevent preference, cost, ranker/AI output, or delivery convenience from bypassing prerequisite, evidence, variant, delivery, rights, or coverage truth. |
| D-058 | Logical runtime and trust boundaries remain binding when deployables are co-located. | `../design/06-implementation-stack.md` | Deployment economy must not permit bypass of Go product authority, cross-runtime contracts, or least-privilege isolation. |
| D-059 | Required asynchronous continuation is durably registered with, or recoverably derivable from, authoritative committed state before an acknowledged operation may depend on it. | `../design/04-application-flows.md` | Closes the commit→crash→lost-work window without mandating a broker or one outbox technology. |
| D-060 | Domain unresolved/negative outcomes are distinct from transport, operation-contract, and infrastructure failures. | `../design/05-api.md` | Evidence, target-support, CoverageGap, content-availability, and pending states must remain truthful domain results rather than system failure or learner weakness. |
| D-061 | Next.js server-side execution remains Web/presentation authority and cannot become a second product backend. | `../design/06-implementation-stack.md` | App Router server capabilities must not duplicate Go persistence, policy, access, or public-API authority. |
| D-062 | Each machine boundary evolves from one contract authority with explicit compatibility discipline; generated bindings remain derived. | `../design/05-api.md`, `../design/06-implementation-stack.md` | Prevent silent deployed-consumer breakage and handwritten cross-language interface drift while preserving canonical semantic ownership. |
